# Reflection

The most challenging part of this assignment was making the same model artifact work reliably across local Python, Docker, and Kubernetes. Training a classifier by itself is straightforward, but deployment introduces several interfaces that all have to agree: the checkpoint must contain enough metadata to rebuild the model, the serving process must use exactly the same preprocessing as training, and every container and Kubernetes volume must refer to the same file path. A small mismatch in any one of these areas can produce a healthy-looking container that cannot make predictions.

I addressed this by treating the checkpoint as a contract. The training script saves the architecture name and number of classes together with the model weights. The FastAPI service reads those fields, rebuilds the correct network, loads the state dictionary on the CPU, and reports an unhealthy status until loading succeeds. I also reused the validation transform from the dataset module instead of copying normalization values into the API. This reduced duplication and made the inference path easier to test and explain.

Kubernetes storage required the most careful infrastructure reasoning. The training Job writes both downloaded data and the best checkpoint to a persistent volume. An init container creates separate data and checkpoint directories before the main container mounts them through `subPath`. The serving Deployment then mounts only the checkpoint directory as read-only. This arrangement lets training and serving share an artifact without letting the API accidentally modify it. Health probes, resource limits, rolling updates, and a minimum of two replicas make the service behave more like a production workload than a single local process.

The assignment also reinforced that reproducibility is more than setting a random seed. Dependency versions are pinned, configuration lives in YAML and a ConfigMap, logs are JSON lines, Docker images have separate dependency sets, and CI runs linting, unit tests, and image builds. If I extended this project, I would add an object store or model registry instead of sharing a filesystem, record experiment metrics in a tracking system, scan images for vulnerabilities, and run an automated smoke prediction after every deployment.
